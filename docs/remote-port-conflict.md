# `remote port forwarding failed` 故障说明

## 现象

OpenVPN 中断后，autossh/ssh 会退出并尝试重连。远端主机上旧的 SSH 会话可能没有同步释放：

```text
Error: remote port forwarding failed for listen port 15432
```

此时新的 SSH 会话认证成功，但远端主机上 `127.0.0.1:15432` 仍由旧 sshd 会话监听。`ExitOnForwardFailure=yes` 会让当前转发启动失败，避免出现“SSH 已连接但端口没有转发”的假成功。

## 先检查监听，不把 TCP 可达当作服务健康

```bash
ssh remote-host "ss -ltnp 'sport = :15432'"
ssh remote-host "nc -z -w 3 127.0.0.1 15432"
```

第二条命令成功只说明远端监听接受 TCP 连接，无法验证转发目标、TLS 证书或 HTTP 服务。残留 sshd 或转发到错误目标的会话也可能通过这个检查。非本应用管理的监听一律显示端口占用，不复用、不标记为已连接，也不启动重复 autossh。

第二条命令失败或超时也不能单凭这一结果确认监听可以终止。应先用对应协议的客户端核验服务和会话用途。

## 安全清理

检查精确端口、PID 和进程：

```bash
ssh remote-host "ss -ltnp 'sport = :15432'"
ssh remote-host "ps -o pid,ppid,user,comm,args -p <PID>"
```

只有在以下条件全部满足时才终止该 PID：

- 监听地址和端口与本隧道完全一致：`127.0.0.1:15432`
- PID 来自该端口的 `ss` 输出
- 进程名是 `sshd`
- 不是当前 SSH 会话本身

```bash
ssh remote-host "kill -TERM <PID>"
```

随后再次检查端口。不要使用 `killall ssh`、`pkill ssh` 或按名称批量终止进程，它们会破坏其他 SSH 会话。

AutoSSH Desk 的“清理端口”按钮会重新读取监听信息，并把诊断结果绑定到 120 秒有效的一次性确认令牌。TCP 可达不会阻止用户在核对用途后显式清理，但界面要求确认中断该 sshd 会话的全部转发；这不是自动判定它为残留。确认清理时再次检查监听和 TCP 状态；若 PID、地址、原始监听信息或 TCP 状态变化，存在多个 PID，或无法确认进程为 sshd，则取消清理并要求重新确认。执行前再次检查精确地址、端口和 PID，并排除当前 SSH 会话的祖先进程。检查、清理和后台重连使用同一隧道锁，避免清理过程中启动新的 autossh。

结束远端 sshd 不会停止发起端的 autossh 或其他自动重连工具。对方仍运行时可能再次占回端口，应先找到并停用发起端，或选择独立的新端口。不要批量终止未知 SSH 客户端。

## 自动恢复，不密集刷日志

启用“自动重连”后，AutoSSH Desk 检测到冲突会停止本次由它启动的 autossh，并进入“远端端口冲突”状态，但不会退出后台监控。应用使用 1、2、5、10、20、30、60 秒退避，达到上限后继续按 60 秒退避检查；实际检查在监控周期内执行。目标网络和 SSH 可达不会跳过端口冲突的退避，避免不断创建失败的 autossh。

- 远端端口释放：自动执行启动前检查并重建隧道，无需再次点击“启动”。
- 原先的非受管监听 TCP 恢复可达：仍按端口冲突处理，不把它当作正确目标。
- 原先的非受管监听释放：重新检查并建立本应用管理的连接。
- 无法确认 TCP 监听状态：只退避重查，不启动重复隧道，也不终止远端进程。
- 手动确认清理后：自动重新检查端口并恢复连接；若端口尚未释放，继续退避等待。

应用不会自动杀死远端占用进程。若旧会话一直不释放，可以使用二次确认的安全清理。手动点击“停止”或关闭“自动重连”会暂停自动连接。SSH 探测的连接重置、连接关闭、超时和无错误输出的非零退出属于可重试故障，不会退出后台监控；已有受管 autossh 时保留进程并重新诊断。明确的认证拒绝、密钥或主机指纹错误、缺少 autossh 仍需人工处理。网络路径变化或系统唤醒时会提前重新诊断。
